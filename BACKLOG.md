- **[Future enhancement, owner-gated] — Exercise-classification-aware fatigue model** `[training-intelligence, correctness]`

  **Status:** Deferred future enhancement. Not a regression or P0. Promote only on explicit owner direction.

  **Lane:** Training Intelligence (follows the PR 477–486 series). No active queue slot yet.

  **Live evidence (2026-06-26):** Heavy Back Squat sessions correctly leave Legs in a high-fatigue state. Accessory work such as Hanging Knee Raises currently contributes a similar "Worked" status for Core, even though the real systemic recovery cost is much lower. The recommendation and coaching surfaces treat both equally because the current readiness model sees only *when* a pattern was trained and *how hard* (via `minRir`), not *what kind of exercise* created that training stress.

  **Root cause (current design):**
  - `services/analytics.js::buildMuscleGroupReadiness` groups all logged sets by movement pattern and runs `recoveryFraction(daysSince, minRir, effortTauMultiplier(intensity))`. This correctly decays harder sessions slower (lower `minRir` → longer tau), but it does not distinguish a heavy compound at RIR 2 from an isolation accessory at the same RIR. A Knee Raise session with `minRir 2` and a Back Squat session with `minRir 2` produce the same recovery tau even though their systemic cost differs by an order of magnitude.
  - `services/muscleVolume.js::weeklyMuscleVolume` credits every set with a flat weight (1.0 primary / 0.5 secondary) regardless of exercise classification, load, or systemic cost.
  - `services/underCoverage.js::computeUnderCoverage` derives `adequate`/`under`/`optimal` status from total effective sets vs MEV targets — no exercise classification weighting. An accessory-only Core week can read as `adequate` even when no meaningful progressive overload was applied.

  **Existing infrastructure already in place (no new vocabulary needed):**
  - `services/exerciseModality.js::modalityFor` already emits a `fatigue_class` field (`high_cns`, `moderate_systemic`, `local`, `metabolic`, `aerobic`, `anaerobic`) for every exercise — but this field is currently unused in the readiness / volume / coverage / recommendation path.
  - `services/liftRole.js` classifies exercises as compound vs accessory; its module comment explicitly flags this as "a stopgap until the Exercise_Catalog carries explicit lift_role / fatigue_class metadata."
  - `services/stimulusGovernor.js::gradeStimulus` already applies different fatigue signals for heavy compounds (`high` on RIR 0) vs isolation (`elevated` or `ok`), and `services/stimulusGovernorRules.js` encodes those distinctions — the vocabulary and rules exist; they are just not wired into the readiness/recommendation path.
  - `recoveryFraction` in `services/analytics.js` already parameterizes the exponential decay tau by `minRir` and `effortTauMultiplier` — extending it with a third axis (`fatigue_class` multiplier) would be a small, contained change.

  **Desired future behavior:**
  - Heavy compounds (`high_cns`: Back Squat, Deadlift, Bench Press, Overhead Press) should produce a longer effective recovery tau — the readiness status reads `fatigued` or `recovering` for proportionally longer.
  - Accessories and isolation work (`local`: Knee Raises, Curls, Face Pulls, Shrugs) should produce a shorter tau — the same readiness status clears to `ready` / `fresh` in 1–2 days regardless of RIR.
  - `moderate_systemic` exercises (rows, dips, pull-ups, Romanian Deadlifts) fall between the two.
  - Workout recommendations (`scoreIntents`, `suggestedWorkout`) and coaching surfaces consume this richer fatigue model, so suggestions are based on meaningful recovery state rather than raw session recency.
