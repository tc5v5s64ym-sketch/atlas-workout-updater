- `[trust-critical]` — could silently corrupt data, produce wrong numbers, or break the preview→approve→write path.

- `[polish]` — wording, ordering, or UX quality. No behavior change.

## Operational resilience — NEEDS TRIAGE (not yet scoped)

A category the backlog has not modelled. Atlas's source of truth is Google Sheets with **no database**, so the runtime plumbing around reads/writes carries real data-trust risk that the coaching-intelligence work does not cover. - ✅ **Schema / header-drift validation** `[trust-critical]` — shipped in two PRs. **PR A** (engine): `validateHeaderRow(actualHeader, expectedColumns, aliases)` in `config/sheetContract.js` (pure, alias/casing-tolerant, position-by-position) + `getHeaderRow(tabName)` in `sheets.js`. **PR B** (wiring): a pre-write header guard in `index.js` reads row 1 of the target tab(s) before any live append and **refuses the write with 409 + `sheet_write:'blocked_schema_drift'`, `sheet_written:false`, `no_write_confirmed:true`** on mismatch, releasing the `write_id`. - ✅ **Sheets write retry/backoff** `[correctness]` (`sheets.js` `appendRows`): `appendRows` now wraps the `values.append` call in `retryWithBackoff` (bounded: 1 initial + 3 retries, exponential 500/1000/2000 ms). **Idempotency-safe retry scope:** `values.append` is NOT idempotent and the `write_id` guard lives in `index.js` (dedupes across HTTP requests, not inside this loop), so `isTransientAppendError` retries **only** on errors where Google rejected the request before touching the sheet — HTTP 429/503 and 403 rate-limit/quota reasons.
