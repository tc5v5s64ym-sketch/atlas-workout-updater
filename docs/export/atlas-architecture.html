Where each responsibility lives, and why:

ComponentLives inReason
Workout parserBackendDeterministic, testable, versioned. Frontend parsing means two parsers drifting apart; AI parsing means non-reproducible logs.
Rules engineBackendSafety decisions must be deterministic and auditable. "Why did Atlas say hold?" must have one answer.
Progress/trend engineBackendComputed from DB, cached, served. Frontend never computes e1RM — it renders it.
AI coachingBackend (ai/ module)The LLM call happens server-side with server-assembled context. Frontend never talks to the LLM directly — that's how you get hallucinated numbers in the UI and leaked API keys.
Memory/contextBackendContext is queried from the DB per request, not accumulated in a chat transcript. The transcript is conversation; the database is memory.
Effort importerBackendImage → vision model → structured candidate → validation → user confirmation → DB. Never image → DB.
Session state during a live workoutBackend (with frontend optimistic mirror)If the phone dies mid-session, the session survives.
ValidationBackend always; frontend additionally for UXFrontend validation is a courtesy. Backend validation is the contract.
The core principle, made operational:

The AI sits in exactly two seats, both advisory: (1) Fallback intent classifier — when the deterministic parser returns low confidence, the AI converts text to a structured intent proposal that goes back through the same validation as parser output. The AI's output is never trusted more than the parser's; it's trusted less (lower confidence ceiling, always flagged for confirmation). (2) Explainer/conversationalist — it receives structured facts (recent sessions, rule decisions, trends) and produces prose. It never produces the facts.

The write path is always: structured data → validation → rules check → DB. The AI can propose entries into the top of that funnel. It can never skip a stage. This is the generalization of the approve-before-save pattern already proven in the prototype.

2. Recommended Backend Architecture

Node.js + Express is right. The workload is I/O-bound JSON plumbing with one external LLM call — Node's sweet spot. No reason to deviate.

Two structural rules that matter more than the file names:

  • Repositories are the only code that touches the DB. Services call repos. This is what makes the Sheets→Postgres swap a one-file change.
  • ai/ may import from services/ and schemas/. Nothing imports from ai/ except chatController and intentFallback consumers. The AI layer is a leaf, not a trunk. If sessionService ever imports atlasCoach, the architecture has failed.

3. API Endpoint Design

All endpoints: Authorization via API key header now, JWT later (see §11). All responses share an envelope: { ok, data, warnings[], error }. Validation failures return 422 with field-level errors.

POST /api/parse-workout-text

Owner: parseController → workoutLanguageParser (+ intentFallback if low confidence). AI: fallback only. Purpose: convert raw text to structured intent. Never writes to DB. Pure function over text + minimal context.

// Request
{ "text": "Bench 135 10/5 185 8/3 225 5/2", "session_id": "uuid-or-null" }

// Response (success)
{
  "ok": true,
  "data": {
    "intent": "log_sets",
    "confidence": 0.97,
    "parser": "deterministic",
    "parser_version": "1.4.0",
    "sets": [
      { "exercise_raw": "Bench", "exercise_id": "ex_bench_press", "weight": 135, "reps": 10, "set_count": 5, "rir": null },
      { "exercise_raw": "Bench", "exercise_id": "ex_bench_press", "weight": 185, "reps": 8, "set_count": 3, "rir": null },
      { "exercise_raw": "Bench", "exercise_id": "ex_bench_press", "weight": 225, "reps": 5, "set_count": 2, "rir": null }
    ],
    "clarifications": []
  }
}

POST /api/start-session — AI: no

// Request
{ "date": "2026-06-10", "location": "Gym", "planned_focus": "push" }
// Response
{ "ok": true, "data": { "session_id": "ses_abc", "status": "active", "started_at": "2026-06-10T17:02:00Z" } }

Validation: only one active session per user (409 if one exists, returning its id so the client can resume); date within ±1 day of now unless explicitly backdating.

POST /api/log-set — AI: no

The hot path. Must be fast and unconditional once data is valid.

// Request
{ "session_id": "ses_abc", "exercise_id": "ex_bench_press", "weight": 205, "reps": 6, "rir": 2, "source": "ui" }
// Response
{
  "ok": true,
  "data": { "set_id": "set_991", "set_number": 3 },
  "warnings": [],
  "rule_flags": [
    { "rule_id": "rir_caution", "severity": "info", "message": "RIR 2 at 205 — this is the consistency target for bench." }
  ]
}

POST /api/log-session — AI: no

Batch path: full parsed session in one call.

// Response
{ "ok": true, "data": { "session_id": "ses_def", "sets_created": 11, "prs_detected": [], "duplicate_check": { "is_probable_duplicate": false } } }

Duplicate detection: same date + >70% overlapping exercise/weight/reps → 409 with matching session id, requiring an explicit force: true to override.

PATCH /api/session/:id/set/:setId — AI: no

// Request
{ "weight": 225, "reps": 6, "correction_source": "user_text", "raw_text": "actually that last set was 6 not 5" }
// Response
{ "ok": true, "data": { "set_id": "set_991", "previous": { "reps": 5 }, "current": { "reps": 6 } } }

Corrections never overwrite silently: previous values go to a set_revisions append.

POST /api/finish-session — AI: no

// Response
{
  "ok": true,
  "data": {
    "session_id": "ses_abc",
    "summary": { "duration_min": 58, "total_sets": 14, "total_volume": 12450, "exercises": 4 },
    "prs": [ { "exercise_id": "ex_bench_press", "type": "rep_pr", "detail": "205×6 @ RIR 2 — best 6 at this weight" } ],
    "rule_decisions": [ { "exercise_id": "ex_bench_press", "decision": "hold", "rule_id": "bench_hold_205_until_clean_6s", "reasoning": "2 of 3 required clean sets of 6 at RIR≥2. One more session." } ],
    "effort_prompt": true
  }
}

POST /api/log-effort — AI: vision model for screenshot extraction only

// Manual request
{ "session_id": "ses_abc", "duration_min": 58, "active_calories": 412, "total_calories": 540, "avg_hr": 121, "peak_hr": 162, "source": "manual" }

// Screenshot path: returns CANDIDATE, not committed:
{ "ok": true, "data": { "status": "needs_confirmation", "candidate": { "duration_min": 58, ... }, "candidate_id": "eff_cand_77" } }
// Then POST /api/log-effort/confirm { "candidate_id": "eff_cand_77" }

GET /api/today — AI: no (pure rules + history)

{
  "ok": true,
  "data": {
    "active_session": null,
    "last_session": { "session_id": "ses_xyz", "date": "2026-06-08", "focus": "push" },
    "plan": [
      {
        "exercise_id": "ex_bench_press",
        "target": { "weight": 205, "reps": 6, "sets": 3 },
        "decision": "hold",
        "reasoning": "Hold 205 until clean 6s at RIR 2.",
        "confidence": "high",
        "last_performance": "205: 6/5/5 @ RIR 2/1/1"
      }
    ]
  }
}

POST /api/chat — AI: yes (the only endpoint where the LLM generates the response)

// Request
{ "message": "should I go up on bench next time?", "conversation_id": "conv_5" }
// Response
{
  "ok": true,
  "data": {
    "reply": "Not yet. You got 6/5/5 at 205 with RIR dropping to 1 on the last two sets. The standard is three clean sets of 6 at RIR 2. You're one good session away — get that, then we load to 210.",
    "structured_actions": [],
    "facts_used": [ "session:ses_xyz", "rule:bench_hold_205_until_clean_6s" ]
  }
}

If the model proposes an action, it returns a structured_actions array validated against intentSchema — the frontend renders a confirm card and only then calls /api/log-set. The model's prose never directly mutates state. facts_used enables auditing hallucinations.

4. Database Schema

Postgres. UUIDs for PKs. Every table gets created_at/updated_at. Every domain table gets user_id now — one user row, no auth complexity, but no painful backfill later.

TableKey columnsWhy it exists / design notes
users id, email unique, display_name Exists so every other table has a real FK target. Index: email.
user_preferences user_id FK, key, value (jsonb) Key-value because preferences churn — don't make each one a migration. Unique(user_id, key).
exercises user_id nullable, canonical_name, muscle_group, lift_code, is_active The canonical catalog. Per-user rows allow custom exercises without polluting the global catalog. Index: (user_id, canonical_name).
exercise_aliases exercise_id FK, alias, source (seed/parser_learned/user_confirmed), confidence Where "Ohp→Overhead Press", "Lats→Lat Pulldown" live. Confirmed match once → write alias → parser never asks again. This makes vocabulary data rather than code. Index: alias (parser's hottest lookup).
sessions user_id FK, date, status (active/finished/abandoned), total_volume, source Partial index on status='active' enforces the one-active-session rule cheaply.
sets session_id FK, exercise_id FK, weight, reps, rir nullable, source, parser_event_id FK nullable, deleted_at nullable Absence of RIR is signal — never default it to a number. parser_event_id links committed sets to the raw text that produced them.
set_revisions set_id FK, previous_values (jsonb), changed_fields (text[]), correction_source, raw_text PATCH updates the live row and appends here. You can always answer "what did the parser originally hear vs. what did the user fix it to" — the data Codex needs to improve the parser.
effort_logs session_id FK unique, duration_min, active_calories, avg_hr, peak_hr, source, screenshot_extraction (jsonb) Unique on session_id. Raw extraction stored alongside confirmed values gives an accuracy corpus for the vision pipeline.
bodyweight_logs user_id, date, weight, notes Build now (one migration), wire UI later.
session_notes session_id FK, text, tags (text[]) Separate from sessions because notes arrive mid-session via chat. Tagged pain notes feed safetyRules.
parser_events raw_text, parser_version, output (jsonb), confidence, resolution, fallback_used Parser flight recorder and regression-test gold mine. Every weird string becomes a future test fixture.
ai_coach_events user_message, context_snapshot (jsonb), reply, structured_actions (jsonb), facts_used (text[]), model, tokens When the AI says something wrong, you can see precisely what context it had. Hallucination debugging is impossible without this.
recommendations session_id nullable (filled when logged), payload (jsonb), rule_ids (text[]) Enables plan-vs-actual adherence measurement later.

Raw vs. parsed vs. corrected: raw text → parser_events.raw_text (immutable). Parsed output → parser_events.output (immutable) and, on commit, sets rows linked via parser_event_id. Corrections → live values on sets, history in set_revisions. Three layers, nothing ever destroyed.

Multi-user without overbuilding: user_id on every table + a single seeded user + API-key auth resolving to that user. No orgs, no roles, no tenancy middleware. That's it. Resist anything more.

5. Workout Parser Integration

Pipeline

raw text
  → intentClassifier (cheap regex/keyword pre-pass: log? command? question? effort?)
  → workoutLanguageParser (deterministic grammar)
      ├─ confidence ≥ 0.9 → schema validation → rules validation → commit (or confirm-card if batch)
      ├─ 0.5–0.9          → clarification question to user → re-parse with answer
      └─ < 0.5            → ai/intentFallback → intent proposal → ALWAYS user-confirmed → same validation → commit
  → parser_events row written in ALL cases, including failures
  → committed sets trigger rule flags → flags travel back in the response
  → (chat-originated only) atlasCoach renders the confirmation/coaching line

The AI fallback's ceiling: its proposals are never auto-committed regardless of its self-reported confidence. Deterministic-high is the only auto-commit tier.

Parser Output Contract (schemas/parserOutputSchema.js)

{
  "parser_version": "1.4.0",
  "intent": "log_sets | correct_set | finish_session | start_session | effort_capture | plan_request | question | unknown",
  "confidence": 0.0,
  "sets": [],
  "correction": null,
  "clarifications": [],
  "unparsed_fragments": [],
  "warnings": []
}

Set object: { exercise_raw, exercise_id|null, alias_confidence, weight, weight_unit, reps, set_count, rir, is_warmup, source_fragment }. source_fragment is the exact substring that produced the set — essential for clarification UX and debugging.

Grammar conventions to encode

In Dale's shorthand, WEIGHT REPS/SETS is the dominant pattern (135 10/5 = 135 for 10 reps × 5 sets). Repeated weight groups chain (185 8/3 225 5/2). Bare REPS/SETS after a group inherits the weight (240 5/2 5/1). x3 is a set multiplier. When two readings are grammatically valid, emit a clarification — the parser's prime directive is never guess silently.

Examples through the contract

Successful parse — "Ohp 95 10/4 105 10/2 10/2":

{ "intent": "log_sets", "confidence": 0.96,
  "sets": [
    { "exercise_raw": "Ohp", "exercise_id": "ex_overhead_press", "alias_confidence": 1.0, "weight": 95, "reps": 10, "set_count": 4 },
    { "exercise_raw": "Ohp", "exercise_id": "ex_overhead_press", "weight": 105, "reps": 10, "set_count": 2 },
    { "exercise_raw": "Ohp", "exercise_id": "ex_overhead_press", "weight": 105, "reps": 10, "set_count": 2 }
  ], "clarifications": [] }

Ambiguous parse — "Lats 170 8/2 x3":

    "fragment": "x3",
    "question": "Does x3 mean 3 total sets of 170×8, or repeat the 2 sets three times (6 sets)?",

6. AI Coaching Layer

System prompt structure

[IDENTITY]      Atlas: direct, concise strength coach. Short replies. No hype.
[HARD RULES]    1. Only state numbers present in CONTEXT blocks. If a number
                   isn't there, say you don't have it.
                2. Never invent sessions, sets, or effort data.
                3. RULE_DECISIONS are final. Explain them; never override them.
                   If the user pushes back, restate the criterion to beat.
                4. To log/correct data, emit a structured_action JSON block —
                   never claim the data "is logged."
                5. RIR 0–1 reported → acknowledge effort, counsel caution,
                   never celebrate grinding.
                6. Pain mention → stop coaching the load, flag it, suggest the
                   note be tagged.
[OUTPUT FORMAT] reply: ≤4 sentences default. structured_actions: array,
                usually empty, validated downstream.

Context blocks injected per request (~2–3k tokens budget)

<USER_PROFILE>     name, units, training age, stated goals, injury history tags
<ACTIVE_SESSION>   (if any) started 17:02 · bench: 135×10, 185×8, 205×6@RIR2, 205×5@RIR1
<RECENT_SESSIONS>  last 5, compressed one line each:
                   06-08 push 52min · bench 205: 6/5/5 @RIR 2/1/1 · ohp 105: 10/10
                   06-06 legs 61min · squat 205: 7/6/6 @RIR 2/2/1 · PR: rep
<EXERCISE_STATE>   bench — HOLD at 205 · criterion: 3×6 @RIR2 · progress: 2/3 · e1RM: +2.1%/30d
<RULE_DECISIONS>   verbatim output of progressionRules/safetyRules incl. rule_id and reasoning
<PREFERENCES>      "no grinding singles", "protect left shoulder", units=lb
<CONVERSATION>     last ~10 turns of this conversation only

The compressed one-line session format matters: it's dense, unambiguous, and cheap. Don't inject raw JSON rows — the model wastes attention re-parsing them.

Few-shot examples (4–6 exchanges, highest-leverage)

  1. User asks to add weight early → model cites the rule criterion and holds the line.
  2. User logs a set in chat → model emits structured_action, replies "Got it — confirm and I'll log 205×6."
  3. User asks about a lift with no history → model says it has no data, asks one question.
  4. User reports a grindy set → acknowledgment without celebration, caution note.
  5. User mentions pain → load coaching stops, note-tagging suggested.

Enforcement beyond prompting

structured_actions validate against intentSchema or get dropped with a logged failure. A post-pass regex extracts weights/reps from the reply and checks them against facts_used context — mismatches flag the event for review. The model literally cannot write to the DB because no tool/route exists for it.

7. Rules Engine

Every rule is a pure function: (history, currentSession, config) → { decision, rule_id, severity, reasoning, criterion_progress }. Decisions are data, stored with the session, and the AI receives them verbatim. Dale's logic ships as the default config, expressed as parameters — not as code — so rule shapes generalize while his numbers stay his.

Progression rules

RuleLogicExample config
hold_until_clean Hold load until N sessions with all working sets ≥ target reps at RIR ≥ threshold Bench: { load: 205, target_reps: 6, min_rir: 2, required_sessions: 3 }
rep_ladder_before_load After hitting rep pattern A, target pattern B before loading Squat: after 205×7/6/6, target 7/7/6 or 7×3, then +load
load_increment When criterion met: +5 lb upper, +10 lb lower (config per lift) —
progression_pathway Meta-rule: hold weight → build reps → build RIR consistency → then load. A lift is always in exactly one phase. —

Safety rules

RuleTriggerOutput
rir_cautionAny working set at RIR ≤ 1Info flag; reply tone shifts to caution; never blocks the log
rir_driftSession-over-session RIR at same load declining (2→1→1)Warning: "fatigue accumulating at this load" — drifting sessions don't count as clean
junk_rep_guardRep PR at RIR 0PR recorded with quality: grind — not celebrated
deload_warningNo progress in N sessions + RIR driftSuggest −10% for one session (advisory)
missed_repsWorking set below target by ≥2 repsFlag; 2 consecutive missed sessions → escalate toward deload
pain_flagNote/chat tagged painHard flag; AI must not coach load increases on that lift until user clears it
impossible_valuesweight >1500, reps >100, RIR >10, e1RM jump >15% in one sessionReject at validation (422), never store
duplicate_sessionSame date + >70% set overlap409 + matching session id; require force

PR detection (in progressService, quality-gated by rules): weight PR, rep PR at weight, e1RM PR — each recorded with quality: clean | grind from RIR. Only clean PRs get celebrated. That single design choice operationalizes "do not celebrate junk reps."

8. Conversation Design

Atlas's voice in one line: a good training partner who keeps the logbook and isn't impressed easily. Templates (the AI paraphrases — these set length, tone, and information order):

TriggerResponse template
"What are we doing today?" Push day. Bench at 205 — the standard is still three clean 6s at RIR 2, you've got two. OHP after, 105 for 10s. Same lat work as Friday unless something's bugging you.
Clean set logged 205×6 at RIR 2. That's two clean sessions — one more like this and we load to 210.
Grindy set logged Logged, 205×6 at RIR 0. That one cost you. It counts as reps but not toward the standard — I want those 6s with two left in the tank.
Milestone (clean) That's the third clean session at 205. Standard met. Next bench day: 210, and don't be surprised if reps dip to 5s for a week — that's normal, not a problem.
Asks to add weight early Not yet. Last session was 6/5/5 with RIR falling to 1 — that's strength being built, not strength ready to load. Beat the standard first: three sets of 6 at RIR 2. You're close.
Finishes session Done — 14 sets, 12,450 lb total, 58 minutes. Bench moved the needle today. Got your Watch data?
Parser clarification Quick check on "Lats 170 8/2 x3" — three total sets of 170×8, or the two sets repeated three times (six total)?

Anti-patterns (enforced in system prompt): no exclamation stacking, no "Great job!! 💪", no restating what the user just said at length, no hedging walls, no corporate safety boilerplate — caution is expressed as a coach would ("that one cost you"), not as a liability disclaimer.

9. App / UI Implications

The frontend's job description: render backend state, capture input, stay dumb.

  • Live session state: backend owns the active session; frontend holds a local mirror keyed by session_id. On app open, GET /api/today reports any active session and the client rehydrates — a dead phone battery never loses a workout.
  • Optimistic logging: render the set immediately as pending, reconcile on the /api/log-set response (which carries the authoritative set_id and any rule_flags). On failure, the row turns into an error state with retry — never silently vanishes.
  • Set editing: every set row is tappable → edit sheet → PATCH. Show a subtle "edited" mark when revision_count > 0.
  • Pending clarification state: a parser clarification is a blocking card attached to the specific text submission — option chips from the parser's clarifications[].options, plus a "let me retype it" escape hatch. The session keeps accepting other input; only the ambiguous fragment is held.
  • Confirm cards: parser-batch commits and AI structured_actions render as the same component — proposed data table + Confirm/Edit/Discard. One pattern, learned once.
  • Manual fallback: the structured set-entry form is always one tap away. Parser fails, chat is down — logging still works.
  • Chat + structured hybrid: chat input routes through /api/parse-workout-text; recognized logs materialize as set rows (with confirm card), and conversation goes to /api/chat. The user shouldn't have to choose modes — intentClassifier chooses for them.
  • Progress tab: exactly two calls — /api/progress/overview for landing, /api/exercises/:id/progress on drill-in. No client-side aggregation, no e1RM math in JS.
  • Effort modal: triggered by effort_prompt: true at finish. Two paths: manual fields, or photo → candidate display with per-field edit → confirm. Extracted values are shown as editable, never auto-committed.

12. Final Recommendation

Build next, in order: the parser test corpus, then the parser, then the parser endpoint with parser_events logging (steps 1–4). Nothing else matters until text reliably becomes structured data, because every other component — rules, recommendations, AI coaching — consumes that output. Then the DB adapter interface and session contract (step 5), because that's the moment Sheets stops being a load-bearing wall.

Do not build yet: offline mode, multi-user auth beyond a user_id column, the Fuel tab, nutrition anything, voice input, social features, a recommendation ML model, or any rules-engine sophistication beyond Dale's actual current logic. Every one of these is a real future feature and a fake current priority. Also do not "improve" the AI by giving it more autonomy — the constraint is the design.

Freeze as contracts now, version them, and treat changes as breaking:

  1. Parser output schema (§5) — the keystone contract. Codex builds against it, the backend consumes it, the test corpus validates it.
  2. Set/session schema (§4) — every engine reads these shapes.
  3. Rule decision shape — { decision, rule_id, severity, reasoning, criterion_progress } — consumed by API responses, the AI context, and the UI alike.
  4. The write-path invariant — structured → validated → rules-checked → committed, with the AI permanently outside the gate proposing, never writing.
The prototype already proved the most important instinct: approve-before-save, dry-run proofs, deterministic enrichment with AI nowhere near the write path. The architecture above is that same instinct applied to the whole system. Atlas becomes a real conversational training system precisely to the degree that the conversation is a view over trustworthy structured data — and a chatbot stapled to a UI to the degree that it isn't. The parser corpus is the next commit. Start there.
